Orientation

What is Vulhub?

Vulhub is a free, open-source collection of pre-built vulnerable environments. Each one is a real piece of software (Apache, Struts, Log4j, WebLogic…) packaged with a known CVE so you can practice exploiting it safely and reproducibly. No hunting for old installers, no fragile setup — just docker compose up and the vulnerable target is live.

🧱 Pre-built & reproducible

Every environment is a Docker image with the exact vulnerable versions baked in. It works the same on every machine.

🎯 Maps to real CVEs

Folders are named after the flaw they contain. You're not practicing toy bugs — these are the same vulnerabilities behind real-world breaches.

📖 Self-documenting

Each environment ships a README explaining the vulnerability and how to reproduce it, with links to the original research.

Where it fits the bigger picture. Vulhub is your sandbox for Phase 3 — Gaining Access from Module 01. You practice the exploitation step against a safe copy of a real target before you'd ever do it on an authorized engagement.
Get ready

Setup — you only need Docker

Vulhub itself isn't "installed." You just need Docker and Docker Compose, then you grab the Vulhub files. Pick your OS:

The native home for Docker — best performance and fewest surprises. On your lab VM:

# Install Docker Engine + Compose plugin (Debian/Ubuntu)
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER      # log out/in so you can run docker without sudo

# Grab Vulhub
git clone https://github.com/vulhub/vulhub.git
cd vulhub

Install Docker Desktop with the WSL2 backend. Then clone Vulhub inside your WSL2 Linux distro for best results.

# In PowerShell: enable WSL2, then install Docker Desktop (WSL2 backend)
wsl --install

# Inside your WSL2 distro:
git clone https://github.com/vulhub/vulhub.git
cd vulhub
Course note. If you're doing this on a Proxmox VM off campus, connect the VPN first — see the Computer Skills guide.

Install Docker Desktop for Mac (Apple Silicon or Intel), then clone Vulhub.

# After installing Docker Desktop:
git clone https://github.com/vulhub/vulhub.git
cd vulhub
Heads-up (Apple Silicon). A few older images are x86-only and may run under emulation or not at all. Most environments are fine.

Confirm Docker is alive before you start:

docker --version && docker compose version
Find your way

How to navigate Vulhub

The layout is simple once you see the pattern. Everything is organized by software, then by CVE:

vulhub/
├── log4j/
│   └── CVE-2021-44228/      ← one environment = one vulnerability
│       ├── docker-compose.yml    the lab definition
│       └── README.md             what it is + how to exploit it
├── struts2/
│   └── s2-045/              (CVE-2017-5638 — the Equifax bug)
├── weblogic/
│   └── CVE-2017-10271/
└── ...                       hundreds more, grouped by product

🗂️ The folder name is the lesson

A path like log4j/CVE-2021-44228 tells you the product and the exact flaw. Search the repo or browse vulhub.org by name.

📖 Always read the README first

Each environment's README.md explains the vulnerability, the affected versions, the exact reproduction steps, and links to the original write-up. It's your walkthrough — don't skip it.

Pro moves

Tips & tricks

Small habits that save hours. Click to expand.

Take a VM snapshot before a session. If an exploit makes a mess or a container won't clean up, you roll back in seconds instead of rebuilding.

Forgot which lab is up, or which port it's on? docker ps lists running containers and their port mappings.

docker ps                 # what's running + ports
docker compose logs -f    # live logs for the current environment

Images add up fast. When a lab is done and torn down, prune what you no longer need.

docker system df          # see what's using space
docker system prune       # remove stopped containers + dangling images

As you exploit, ask: which pentest phase is this? Mapping each lab to Recon → Scan → Access cements the methodology, not just the one trick.

Screenshot your proof, jot the command that worked and the CVE. You're building the reporting muscle from Phase 5 — and great notes for the exam.

Why it matters

Real breaches you'll practice on

These aren't academic toys. Each card below is a vulnerability that caused a real-world incident — and a Vulhub environment lets you safely recreate it. Hover a card to lift it.

Dec 2021

Log4Shell — the internet's worst week

CVE-2021-44228 · Apache Log4j

A single crafted string in a log message gave attackers remote code execution. Because Log4j is buried in countless Java apps, it triggered a global, frantic patching scramble.

🐳 Practice it: log4j/CVE-2021-44228

2017

Apache Struts → the Equifax breach

CVE-2017-5638 · Struts2 (s2-045)

An unpatched Struts flaw let attackers run commands on Equifax servers, exposing personal data on ~147 million people — one of the most consequential breaches ever.

🐳 Practice it: struts2/s2-045

2022

Spring4Shell

CVE-2022-22965 · Spring Framework

A class-binding flaw in the hugely popular Spring framework allowed RCE on many Java web apps, prompting another rapid round of emergency patching.

🐳 Practice it: spring/CVE-2022-22965

2022

Confluence OGNL injection

CVE-2022-26134 · Atlassian Confluence

Actively exploited as a zero-day, this let attackers run code on Confluence servers worldwide before a fix existed — a classic "patch now" emergency.

🐳 Practice it: confluence/CVE-2022-26134

2018

Drupalgeddon2

CVE-2018-7600 · Drupal

A pre-auth RCE in the Drupal CMS was mass-exploited within days of disclosure to plant cryptominers and backdoors across thousands of sites.

🐳 Practice it: drupal/CVE-2018-7600

2014

Shellshock

CVE-2014-6271 · GNU Bash

A decades-old Bash parsing bug let attackers execute commands via web requests, CGI scripts and more — devastating because Bash is everywhere on Unix systems.

🐳 Practice it: bash/CVE-2014-6271

CVE IDs link to the canonical record at NIST's National Vulnerability Database. Confirm the exact Vulhub path in the repo — folder names occasionally change.

When it breaks

Troubleshooting

Another container (or app) is using that port. Tear down the previous lab with docker compose down, or run docker ps to find and stop the conflicting container.

Docker isn't running (start Docker Desktop / the service) or your user isn't in the docker group. On Linux: sudo usermod -aG docker $USER, then log out and back in.

Give the container a few seconds to finish booting, then check the exact port with docker ps — it's listed in the README and may not be the default. Check logs with docker compose logs.

Check your internet/VPN, then retry. On Apple Silicon some x86-only images need emulation. As a last resort, docker compose pull first, then up.
